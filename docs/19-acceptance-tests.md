# Приёмочная проверка XiControl: результаты и границы

Проверка 2026-10-19 на Xiaomi Book Pro 14 TM2424 / Intel Core Ultra X7 358H, Windows x64,
Intel IPF 2.3.20201.4882. Начальная сборка — fork.4 (`79daa01`); выявленные дефекты исправлены
в ветке `fix/acceptance-context-and-ui` перед выпуском fork.5.

была создана и удалена. Автозапуск оставлен выключенным, как до теста.

## 13 сценариев настоящего редактора

1. Активный профиль автоматически подставляет точные 30/50 Вт.
2. Активный режим показывает действие «Сохранить и применить».
3. Выбор другой плитки не вызывает ни OEM SET, ни запись мощности.
4. Неактивный неизменённый профиль не требует повторного сохранения.
5. PL1 > PL2 блокирует сохранение.
6. Черновики разных режимов сохраняются при переключении плиток.
7. «Отменить изменения» возвращает сохранённые значения выбранного режима.
8. Неактивное сохранение вызывает единый save-only callback без Apply.
9. Сохранённые ватты отображаются в плитке.
10. Черновики одного режима на AC/DC независимы.
11. После свежего чтения чистый шаблон обновляется с 40/65 до 20/30.
12. Статус смены контекста не показывает прежние ватты как текущие.
13. При неизвестном снимке остаётся доступно обновление данных.

Это автоматизированные действия над настоящими контролами в тестовом хосте, а не утверждение,
что весь UI установленного elevated exe прокликан внешней автоматизацией. Подтверждение Yes
в модальном предупреждении и запись из UI проверены по частям: production UI → callback на фейках,
затем тот же production controller/session → реальная аппаратная запись с UAC.

## Проверка запуска готового EXE

Первый внешний поиск значка не нашёл его и дал отрицательный результат, хотя процесс был жив.
Дополнительное перечисление настоящего taskbar/overflow через UI Automation обнаружило причину:
Windows поместила значок в `TopLevelWindowForOverflowXamlIsland`, а accessible name начиналось с пробела.
После `TrimStart` и раскрытия overflow реальный `NotifyItemIcon` найден. Его `Invoke` сделал одно
из окон XiControl видимым; далее стандартное Escape + контекстное меню + «Выход» завершили процесс.
Повторная проверка процессов подтвердила отсутствие XiControl. Принудительного завершения не было.
Это исправление диагностического локатора, не дефект запуска приложения. Исходный неуспешный
отчёт не подменялся: сведения повторной попытки сохранены отдельно в локальном `attach-tray.json`.

## Найденные и исправленные дефекты

- **Откат не был привязан к OEM-режиму.** После Fn+K/другого пути новый режим с такими же
  ваттами мог ошибочно считаться владельцем старого cap. Теперь journal и baseline хранят режим,
  перед каждым SET проверяется известный совпадающий режим + AC/DC + поколение. В чужом/неизвестном
  режиме откат запрещён, журнал сохраняется. Старые журналы без режима не дают разрешения на запись.
- **Старые данные после смены питания/сна.** Снимок, baseline и Mode очищаются, применение отключено,
  Changed виден в редакторе. Открытое окно отслеживает готовый DTO и источник без новых аппаратных GET.
- **Чистый шаблон редактора оставался устаревшим после Refresh.** Чистые поля теперь обновляются;
  действительно изменённый черновик не теряется. При отсутствии свежего снимка известные значения
  не заменяются фиктивным 10/10.
- **Ошибка чтения/отката могла оставить старую подпись текущих ватт.** Неуспешная операция теперь
  публикует неизвестный Current, а не подтверждает прежний снимок.

Дополнительно добавлены регрессионные тесты смены режима при совпадающих ваттах, между SET1/SET2,
после чтения baseline, неизвестного режима, Dispose в другом режиме и инвалидирования готовности.

## Чего эта проверка не доказывает

По прямому выбору пользователя завершить без disruptive-проверок **не выполнялись**:

- физическое закрытие крышки и подтверждение работы с ней от сети/батареи;
- реальное отключение/подключение зарядки во время UI/аппаратной транзакции;
- системный сон, пробуждение, перезагрузка, logoff/logon и автозапуск после входа;
- аппаратное применение каждого профиля во всех режимах;
- длительный стресс-тест температуры или физический замер потребления CPU.

Двухсекундное readback подтверждает интерфейс и установленные значения, не гарантирует постоянное
удержание мощности DTT/прошивкой под нагрузкой. 10 Вт остаётся guard приложения, а не подтверждённым
минимумом OEM. Сборка остаётся экспериментальной; формулировка «всё полностью протестировано» неверна.

## Локальные первичные отчёты

Сырые отчёты находятся в рабочей папке `build/acceptance-fixed/ui-results.json`,
`build/acceptance-hardware/hardware-results.json` и `build/acceptance-system/system-results.json`.
Публичная сводка не включает SID, пользовательские конфигурации, установочные пути или резервные
копии профилей. В аппаратном отчёте подтверждены `ProfilesRestored=true`,
`OriginalLimitsRestored=true`, `RecoveryPending=false`.
